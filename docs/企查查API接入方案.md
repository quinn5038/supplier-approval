## 一、为什么要接入（一句话版）

**当前 A10 商业信誉规则只检查工商登记状态，缺了失信/被执行人/限消令/经营异常/严重违法 5 项硬拦截**——这些是国企采购最该自动拦截的合规红线，参赛评委只要打开 rules.yaml 一看就知道这块是空的，扣分严重。

接入企查查 API 后，这 5 项拦截能在阶段2（离线审核）自动跑，不需要人工查企查查网页再填写意见。

## 四、4 步实施方案（对现有代码的影响）

### 步骤 1：新建 `qcc_api_client.py` 模块（不动现有代码）

**新建文件**：`supplier_approval_starter/qcc_api_client.py`

封装 16 个接口的调用逻辑：
- 公共方法 `_call(path, params)`：拼接企查查 API URL、加 AppKey 签名、HTTP 请求、解析 JSON
- 16 个具体方法：`fetch_verify(name, code, legal)`、`fetch_baseinfo(name)`、`fetch_dishonest(name)` 等
- 缓存机制：每家供应商调一次后写入 `qcc_results.json`，避免重复调用浪费配额
- 异常处理：API 失败/超时/配额超限 → 记录日志+该维度跳过（不影响其他维度）

**对现有代码影响**：零。新文件。

### 步骤 2：扩展 `qcc_results.json` 数据结构（向后兼容）

每家供应商的数据新增 6 个字段：

```json
{
  "91440101MA5AT8208M": {
    "reg_info": {...},              // 已有
    "accuracy": {...},              // 已有
    "shareholders": [...],          // 已有
    "actual_controller": {...},     // 已有
    "financial": {...},             // 已有（不用）
    "dishonest": [...],             // 新增：失信人列表
    "zhixinginfo": [...],           // 新增：被执行人列表
    "consumption_restriction": [...], // 新增：限制消费令列表
    "abnormal": [...],              // 新增：经营异常名录
    "illegalinfo": [...],           // 新增：严重违法列表
    "punishment_info": [...]        // 新增：行政处罚列表
  }
}
```

旧数据（只有前 5 个字段）照样能跑，新字段缺失时该维度跳过。

**对现有代码影响**：零。`enhance_checklist_with_qcc` 现有逻辑用 `qcc.get("reg_info") or {}` 取数据，新增字段用同样模式，不冲突。

### 步骤 3：扩展 `auto_approve.py` 的 `enhance_checklist_with_qcc` 函数

**A10 商业信誉**从"只看登记状态"升级为"全量司法风险扫描"：

```python
# 伪代码示意
elif cid == "A10":
    # 现有：登记状态检查（保留）
    # 新增：失信/被执行/限消令/经营异常/严重违法
    if qcc.get("dishonest"):
        c["status"] = "fail"
        c["detail"] = f"企查查发现失信记录 {len(qcc['dishonest'])} 条"
        qcc_issues.append("商业信誉：失信被执行人")
    elif qcc.get("zhixinginfo"):
        c["status"] = "fail"
        ...
    elif qcc.get("consumption_restriction"):
        ...
    elif qcc.get("abnormal"):
        ...
    elif qcc.get("illegalinfo"):
        # 严重违法直接退回（161 号文明示）
        ...
```

**A03 纳税信用等级**：用企查查 `m/taxCredit/2.0` 接口拿税务评级（A/B/C/D/M 级），与供应商上传的纳税信用等级证明交叉核实。一致→pass，不一致→fail（提交虚假材料）。

**A02 法人身份证明**：保留现有"中交关联"检查，新增"股权出质"检查（出质比例过高转人工）。

**对现有代码影响**：
- `enhance_checklist_with_qcc` 函数内新增 3 个分支（A10/A03/A02 扩展），原有逻辑不动
- 函数从 ~100 行扩展到 ~180 行
- 备份规则：先 `cp auto_approve.py auto_approve_R8.py`（按 Quinn 备份规则）

## 六、风险点 + 对策

| 风险 | 对策 |
|---|---|
| 企查查 API 配额超限（免费套餐 2000 次/天）| 缓存机制：每家供应商调一次写入 `qcc_results.json`，重跑读缓存不重复调 |
| API 调用失败/超时 | 异常处理：失败维度跳过+记日志，不影响其他维度判定 |
| 数据结构差异（企查查返回字段名跟文档不一致）| 实际接入时打印响应先做字段映射，写在 `qcc_api_client.py` 注释里 |
| API 费率（免费套餐外收费）| 16 接口×31 家=496 次/批，免费套餐足够；新增供应商才调 |
| 接入后规则变严导致大量转人工 | 保守原则保留（业务 8/31 确认）：发现的问题一律转人工，不直接退回（严重违法除外）|
